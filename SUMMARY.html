Protocol Architecture & Design Summary

1. The Problem Space

The system requires transporting 160-byte media frames every 20ms across a hostile UDP network that drops, delays, reorders, and duplicates packets. To produce a valid run, the protocol must maintain a deadline miss rate of ≤ 1.00% and a bandwidth overhead of ≤ 2.00x, while achieving the lowest possible playout delay.

2. Architecture & Design Choices

Why Forward Error Correction (FEC) over ARQ?

An Automatic Repeat Request (ARQ) system relying on a feedback channel requires waiting a full Round Trip Time (RTT) to request and receive a dropped packet. This severely inflates playout delay. Because the grading heavily favors low latency, we chose Forward Error Correction (FEC) via bitwise XOR parity. This preemptively pushes recovery data across the network, allowing the receiver to reconstruct lost frames without requesting them.

Why XOR Parity over 100% Duplication?

Sending two copies of every frame mathematically results in a ~2.05x bandwidth overhead due to the 4-byte sequence headers on the 160-byte payloads. To comfortably beat the 2.00x cap, our sender pairs two consecutive data frames and generates a single XOR parity packet. This limits our bandwidth overhead to an efficient 1.54x (3 packets sent for every 2 frames generated).

The Stateless Receiver

Traditional jitter buffers get stuck waiting for sequential packets (head-of-line blocking). Our receiver is designed as a stateless, instant forwarder. It ignores order and fires data directly to the player port. If an XOR parity packet arrives, the receiver instantly checks if one of its constituent data frames is missing. If a gap is detected, it calculates the missing bytes and forwards the recovered packet immediately.

3. System-Level Implementation Details

  • Bit Hijacking for Parity: The sender uses the highest bit of the 4-byte sequence number (0x80000000) as a flag. The receiver uses a bitwise AND (0x7FFFFFFF) to mask the flag and route the payload to either the data buffer or the parity buffer.
  • Memory Management: To prevent the C++ maps from causing memory leaks during extended runs, the receiver routinely checks sequence numbers and erases packets older than 1,000ms.
  • Non-Blocking Sockets: The receiver does not rely on strict temporal blocking. By reading available bytes as fast as possible, it limits CPU overhead while ensuring it never misses a tight playout deadline.
